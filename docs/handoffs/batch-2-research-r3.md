- Cases: 16 (one positive `must-flag` and one benign `must-not-flag` per slot; the two Zoom families share one pair), each `maintainer-only` with a review history holding the `authored` event and the `decided` event copied from the Batch 2 precedent. Fixtures were appended to the authored sets `elastic-authored`, `hubspot-authored`, `x-authored`, `zendesk-authored` and `zoom-authored` (no existing item edited): 3 or 4 positive layouts and 7 or 8 benign lookalikes per pair.
- Synthetic values: every credential-shaped value is a fixed marker built for these records (`SYNTHETIC-never-issued-<provider>-<role>-000N`; the Zoom Basic tokens are the Base64 of a synthetic `client_id:client_secret` pair). Provider example values in the pages read (token strings, Basic strings, UUID-like placeholders) were not copied and are not stated as a format.

## Boundaries kept

- Refresh tokens belong to token request and response fields, not resource API Bearer headers (G2). Access tokens that sit in the same token responses are not covered by these Cases; the response fixtures omit them.
- The ECE carrier was confirmed on an ECE page, not taken from the Elastic Cloud ApiKey Case; its Case is separate (G4).
- In a Basic envelope the secret exists only inside the encoded credential, so the extent is the whole encoded token, as in the Canva and Figma precedents. Client ids, account ids and HMAC signature outputs are public or derived and are not the secret (G3).
- No scanner status, support policy or product behaviour entered any record.
