## Provable, contextual-only, era-specific, unassertable

- **Provable (provider-documented):** each date and role in the table above, each tied to a pinned capture or a page read on 2026-10-05. Adobe's JWT assertion is derived from the private key and short-lived by recommendation (a few minutes); its identifiers (Organization ID, Technical Account ID, API key) are claims in the payload and are not the key.
- **Contextual-only:** the existing hyphen-grouped 8-4-4-4-12 shape for HubSpot (two rule artifacts, tool-corroborated consistency, unchanged) and the single-artifact leads for Airtable and Dropbox. Nothing here was upgraded. A second-artifact search at the TruffleHog commit already cited found Airtable detectors only for OAuth and personal access tokens and a Dropbox detector only for the `sl.` form, so Airtable and Dropbox legacy forms still have one artifact each.
- **Era-specific:** every date. They are announcements the provider revised (Adobe changed its end-of-life date twice: 2025-01-01, 2025-01-27, 2025-06-30, and the creation cutoff from 2024-05-01 to 2024-06-03). None is a retrospective format-validity interval; `validity` was left null on all four contracts.
- **Unassertable:** the last-working date of any credential in this group, and any format. A credential of these eras found in logs or configuration remains a redaction concern whatever the date; the records do not say it is benign.

- Dropbox legacy issuance: two provider dates conflict and are recorded as an `unresolved` claim `retirement-date-statements-differ` with an open question, not resolved by choosing.
- HubSpot account key versus developer `hapikey`: HubSpot's own 2022 page says they differ only by account type and both travel in `hapikey`; so the distinction is scope and era, not a documented grammar. Which credential the UUID-shaped lead describes stays open. The consequence of 2022-11-30 is worded as "can no longer be used as an authentication method" on one page and "begin the process of deprecating ... at your own risk" on another (`api-key-end-of-use-statements-differ`, `unresolved`).

## Case axes the sources support (no Case authored)

For a later Case or fixture pass, the sources support these synthetic axes, each separable:

- secret input versus derived values: Adobe private key (secret) versus the signed JWT assertion (derived, short-lived) versus the public certificate (verification half) versus `client_secret` (a separate credential beside it in the exchange request);
- public identifiers and companions: Adobe Organization ID, Technical Account ID, API key (Client ID); HubSpot developer account key versus account key (same carrier, different account type); Dropbox app key;
- placeholders and masks: HubSpot `{YOUR_DEVELOPER_API_KEY}` and a masked `hapikey` display (no length or structure is implied);
- carriers: HubSpot `hapikey` query parameter (both key kinds); Airtable `api_key` URL parameter (named indirectly only); Adobe `jwt_token` (the assertion, not the key); Dropbox `access_token` response member without `expires_in`;
- representation boundaries: a multi-line key file (Adobe, encoding unstated, so no value is constructed), a URL query string (HubSpot, Airtable), a JSON response member (Dropbox).

Why no Case: the situations that could meet ADR 0007 need a carrier and a value boundary. Only HubSpot's carrier is clearly documented, and a `must-flag` expectation for it would be a maintainer-only project-policy decision that overlaps the still-current developer key; Adobe's key has no documented encoding or carrier of its own, Airtable's carrier is named only in passing, and Dropbox's date and shape questions are open. Per the issue, this is recorded as a disposition rather than forced. HubSpot `hapikey` is the one row a later maintainer-only Case could start from (follow `docs/handoffs/batch-2-cases-a.md`), with the era claims here as its context.
